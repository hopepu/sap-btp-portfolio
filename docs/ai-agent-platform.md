# AI 에이전트 플랫폼 설계

업무 화면 곳곳에 붙은 AI(요약 배너, 차이 분석 카드, 리스크 카드, 예측, 업무 자동화)를
**도메인마다 따로 만들지 않고 하나의 구조로 관리**하기 위해 설계한 내용입니다.

## 1. 문제

초기에는 화면마다 AI 호출 코드를 따로 작성했습니다. 그러자 다음 문제가 생겼습니다.
- 같은 역할의 프론트 AI 실행기가 4벌로 갈라져, 한쪽만 고쳐지는 사고가 반복됨
- 어떤 화면 카드가 어떤 프롬프트를 쓰는지 코드를 열어 봐야만 알 수 있음
- 도메인(손익·예산·경비·채권채무·AI Office)마다 출력 형식, 저장 방식, 배치 방식이 제각각

## 2. 구조

```mermaid
flowchart TB
  subgraph UI[화면]
    C1[카드 A] & C2[카드 B] & C3[배너]
  end
  subgraph CAT[화면 자리 카탈로그]
    S[(domain · screen_key · slot_key · slot_item)]
  end
  subgraph REG[프롬프트 레지스트리]
    AG[(Agent<br/>이름 · 버전 · 자리 · 출력형식)]
  end
  subgraph TOOLS[도메인 에이전트 레지스트리]
    PL[손익 에이전트] & BG[예산 에이전트] & OF[Office 에이전트]
  end
  UI -->|자리 키로 요청| CAT --> AG
  TOOLS -->|runAgent(이름)| AG
  A2A[A2A 워크플로 엔진] -->|도구명 = 액션명| TOOLS
  A2A --> MCP[MCP 핸들러<br/>메일 · 문서 · Teams · HTTP · AI 추출]
  AG --> LLM[LLM]
```

### 2-1. 화면 자리(Screen Slot) 카탈로그
- 화면의 AI 출력 위치를 `[도메인, 화면 키, 자리 키, 자리 항목, 이름, 설명, 순서]` 한 줄로 등록합니다.
- **카드 N장 = 자리 N줄 = 에이전트 N개.** 카드 하나에 에이전트 하나가 대응해서, 관리 화면에서 카드별로 프롬프트와 출력 형식을 고칠 수 있습니다.
- 자리 조회 API가 각 자리를 어떤 에이전트가 차지했는지(`takenBy`)를 돌려줘, "자리는 있는데 담당 에이전트가 없는" 상태를 바로 찾습니다.
- 저장소를 쓰는 화면은 저장 키에 자리(`slot_key:slot_item`)를 넣어, 카드끼리 저장본을 덮어쓰지 않게 했습니다.

### 2-2. 프롬프트 레지스트리
- 프롬프트는 **이름**으로 호출합니다(GUID 아님). 버전 교체는 백엔드가 `사용 여부 · 현재 버전` 플래그로 고르므로 호출부는 바뀌지 않습니다.
- 출력 필드는 응답 스키마(responseSchema)로 강제하고, 마크다운 골격은 출력 형식 템플릿이 담당합니다.

### 2-3. 도메인 에이전트 레지스트리 → [samples/cap-agent-registry](../samples/cap-agent-registry)
- 도메인마다 `index.js` 하나가 영역 에이전트(요약·차이·리스크·예측·대시보드…)를 모읍니다.
- **계약은 하나: 도구명 = CAP 서비스 액션명.** 이 계약만 지키면 A2A 엔진과 도구 선택기가 새 도메인 도구를 코드 수정 없이 찾습니다.
- 기존 Office 레지스트리에 끼워 넣지 않고 병렬 레지스트리로 둔 이유: Office 쪽은 라우터 힌트·내비게이션까지 맡고 있어, 섞으면 다른 도메인 항목이 Office 화면에 노출됩니다.
- 모든 도구는 같은 `runAgent()` 경로로 프롬프트를 부릅니다. 실패는 빈 문자열이 아니라 **사유가 담긴 JSON**으로 돌려, 워크플로가 "성공했는데 내용이 없는" 상태가 되지 않게 했습니다.

### 2-4. A2A 워크플로
- 여러 에이전트·도구를 단계로 엮은 업무 흐름입니다(결정 노드, API 노드, 사람 승인 대기, 기한 초과 자동 처리).
- 단계별 실행 로그와 시작 시각을 남겨 **시간 준수율·인건비 환산** 같은 운영 지표를 만들고, 프로세스 맵(BPMN)으로 시각화했습니다.
- 16개 시나리오를 순차 등록하며 각 시나리오를 실제 실행으로 검증했습니다.

### 2-5. MCP 도구 핸들러 → [samples/cap-mcp-handlers](../samples/cap-mcp-handlers)
- 외부 도구 실행 함수를 **명시적 레지스트리**로 선언합니다(리플렉션으로 훑지 않음).
  - 화면에 라벨·파라미터·필요 스코프를 함께 내려줄 수 있고
  - 내부 유틸 함수가 실수로 도구로 노출되지 않으며
  - 미구현 핸들러를 화면에서 구분해 보여줄 수 있습니다.
- 모든 핸들러의 시그니처는 `async ({ system, params, config, ctx }) => ({ ok, data, message })` 하나입니다.
- 범용 HTTP 핸들러는 요청/응답 변환기(전처리·후처리)만 이름으로 지정하게 해서, 시스템이 늘어도 핸들러를 새로 만들 필요가 없습니다.
- Destination 필요 여부는 *시스템*이 아니라 *핸들러*가 결정합니다(API마다 호스트가 다르고 자체 토큰을 쓰는 서비스가 있기 때문).

### 2-6. LLM 호출 래퍼 → [samples/cap-llm-json](../samples/cap-llm-json)
- "텍스트를 넣고 스키마대로 JSON을 받는다" 하나만 합니다.
- 기본 temperature 0(같은 입력 → 같은 결과), 추출 작업은 추론 기능을 꺼서 지연을 줄였습니다.
- **잘림을 먼저 판정**: 출력 토큰 상한에 걸려 JSON이 깨진 경우를 "모델이 JSON을 안 줬다"와 구분해 알려 줍니다. 실제로 긴 메일 본문에서 이 문제로 원인을 오래 찾은 경험이 있습니다.

## 3. 결과
- 손익·예산·경비·채권채무·AI Office 5개 도메인의 AI가 같은 구조(자리 → 에이전트 → 출력 형식 → 저장본)로 통일
- 프론트 AI 실행기 4벌 → 공용 1벌
- 관리 화면에서 카드 단위로 프롬프트·출력 형식·정기 배치(월 마감 기준 전 조직 미리 생성)를 운영
