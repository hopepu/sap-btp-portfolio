# 화면 로딩 성능 개선

오픈을 앞두고 "메뉴를 누르면 화면이 늦게 뜬다"는 문제를 받아, **원인별로 측정 → 하나씩 제거**한 기록입니다.
"느리다"는 하나의 문제가 아니라 서로 다른 작은 원인 여러 개였고, 각각은 작은 수정으로 풀렸습니다.

## 1. 측정 방법
- 같은 계정·같은 화면·캐시를 비운 상태에서 브라우저 성능 탭과 네트워크 탭으로 측정했습니다.
- **로컬(`cds watch`)과 배포본을 구분**했습니다. 로컬에서 빨라진 것은 배포본에서 다시 재야 "개선"으로 기록했습니다.
- 원인 하나를 고칠 때마다 다시 재서, 어떤 수정이 몇 초를 줄였는지 따로 남겼습니다.

## 2. 원인과 조치

| # | 원인 | 조치 | 결과 |
|---|---|---|---|
| 1 | 셸이 시작할 때 모든 화면이 느린 공통 요청(최대 약 15초)을 기다림 | 화면 표시와 그 요청을 분리 | 화면 진입 대기 제거 |
| 2 | 대용량 표가 `growing`으로 행을 계속 늘리며 DOM이 수 MB까지 누적 | 렌더링 방식 변경 | 9.0초 → 3.6초 |
| 3 | 한 화면이 같은 비용 데이터를 반복 조회(24회·80회) | 공유 키로 묶어 1회·8회로 축소 | 17.5초 → 7.2초 |
| 4 | 공용 빈 칸 정렬 유틸이 DOM 변경마다 칸을 검색 | 변경을 모아 다음 프레임에 한 번 처리 | CPU 2.1초 → 0.02초 |
| 5 | Tailwind Play CDN이 브라우저에서 매번 CSS를 컴파일 | 빌드된 CSS 파일로 전환, 8개 화면 픽셀 비교 | 컴파일 시간 제거, 화면 차이 없음 |
| 6 | CAP OData `$batch`가 묶인 GET을 **하나씩 차례로** 처리(기본 병렬도 1) | 병렬도 4로 상향 | 34건 묶음이 순차 3.5초 → 4건씩 동시 처리 |

배포본 실측에서 가장 무거웠던 매입계약 화면은 **약 1.5초**로 줄었습니다.

## 3. 사례 상세

### 3-1. CAP `$batch` 병렬도
UI5 OData V4 모델은 여러 요청을 `$batch` 하나로 묶어 보냅니다. CAP은 기본적으로 그 안의 요청을 순차 처리하므로,
요청당 0.1초짜리 34건이 3.5초가 됐습니다. 같은 34건을 따로 병렬로 보내면 0.9초였습니다.

```json
{
  "cds": {
    "odata": {
      "max_batch_header_size": "1024KiB",
      "max_batch_parallelization": 4
    }
  }
}
```
- 요청마다 트랜잭션이 따로인 것은 그대로이므로 쓰기 순서에는 영향이 없습니다.
- 값은 DB 연결 풀 크기(최대 20)를 고려해 4로 정했습니다. 무작정 올리면 동시 사용자 상황에서 풀을 고갈시킵니다.

### 3-2. 공용 유틸의 MutationObserver → [samples/ui5-empty-cell-align](../samples/ui5-empty-cell-align)
기능(빈 칸 판정)은 그대로 두고 "언제, 몇 번 DOM을 찾는지"만 바꿨습니다. 모든 화면이 쓰는 유틸이라 효과가 전 화면에 퍼졌습니다.

### 3-3. Tailwind Play CDN 제거
개발 편의로 넣었던 Play CDN은 브라우저에서 클래스를 스캔해 CSS를 만듭니다. 빌드 단계에서 만든 CSS 파일로 바꾸고,
바꾸기 전후 8개 화면을 픽셀 단위로 비교해 회귀가 없음을 확인한 뒤 배포했습니다.

## 4. 배운 점
- 성능 문제는 "느리다"를 **원인별 측정값**으로 쪼개는 순간 대부분 풀립니다.
- 공용 코드(셸·공용 유틸·프레임워크 설정)의 작은 비용은 화면 수만큼 곱해집니다. 공용 계층부터 의심하는 것이 효율적이었습니다.
- 개선은 반드시 배포본에서 다시 재야 합니다. 로컬은 네트워크·인증·approuter 비용이 빠져 있습니다.
